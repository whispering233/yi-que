# 总体设计

## 项目定位

**一阕**是宋词的创作、鉴赏与交流平台。

差异化立足点：现有同类平台（搜韵、诗词吾爱）的格律校验都需要**提交表单后等待结果**，且校验逻辑在服务端，是无保护的黑盒。一阕把校验引擎做成**纯客户端纯函数**，输入即校验、逐字即反馈，且引擎与词谱数据完全公开——这与 AGPL-3.0 的选择是自洽的。

## 阶段划分

| 阶段 | 形态 | 内容 | 技术面 |
| :--- | :--- | :--- | :--- |
| **C** | 工具站 | 格律校验 + 词谱查询 + 词库浏览检索 | 纯静态，零服务端、零数据库 |
| **B** | 公开社区 | 账号、作品发布、评论、点赞、收藏 | 引入 PostgreSQL 与服务端 |

**C 阶段先行**：工具能力零内容审核风险、零运营成本、可独立发布拿到真实反馈；且它的数据管道与引擎正是 B 阶段社区功能的地基。

## 总体架构

```
                    构建期                                  运行期（浏览器）
  ┌──────────────────────────────┐          ┌──────────────────────────────────┐
  │ 上游数据源（公有领域 / MIT）  │          │  词作详情页   预渲染，零额外载荷   │
  │  钦定词谱原典                 │          │  词牌页 / 词人页  预渲染           │
  │  全宋词文本                   │          │                                  │
  │  拼音表                       │          │  校验页   加载词谱 → 引擎逐字校验  │
  └───────────┬──────────────────┘          │  搜索页   加载语料 → 建索引 → 检索 │
              │                              └──────────────────────────────────┘
              ▼                                        ▲
  ┌──────────────────────────────┐                     │
  │ 数据管道（构建期，含护栏自检）│                     │
  │  清洗 · 归一化 · 紧凑编码     │─────────静态产物─────┘
  │  字体子集 · slug 生成         │
  └──────────────────────────────┘
```

**关键性质**：运行期没有任何动态数据源。校验、检索、辨谱全部在浏览器内完成。上游数据更新 = 重新构建 + 部署，不涉及数据迁移。

## 核心领域概念

宋词的格律体系有严格的层级，这是整个数据模型与引擎的基础。

| 概念 | 说明 |
| :--- | :--- |
| **词牌（调）** | 曲调名，如「浣溪沙」「水调歌头」。一个词牌有多条别名 |
| **词格（体）** | 同一词牌下的不同格式。因字数、句读、平仄差异而分化，分「正体」与「变体」 |
| **正体（定格）** | 词牌的代表格式。取自原典体例——「每调选用唐、宋、元词一首，必以创始之人所作本词为正体……断列李词在前，诸词附后」。即**去重后该词牌的第一个词格** |
| **片（阕）** | 词格由换片标记切分出的段。双调两片，单调一片 |
| **字位** | 词格中每一个字的格律要求，含三项：所属平仄、句读标记、换片标记 |
| **平仄要求** | 三值：平（当用平声）、仄（当用仄声）、中（平仄皆可） |
| **句读标记** | 句（整句）、读（半句/顿）、韵（韵脚位）、叶（通叶）、叠（叠韵）、换（换韵） |
| **韵部** | 字所属的韵类。词林正韵分十九部，中华新韵分十四韵 |
| **韵书** | 韵部与平仄的判定依据。本项目支持词林正韵与中华新韵双轨 |
| **出律** | 某字位的实际平仄与词格要求不符 |
| **多音字** | 一字多读，平仄不定。须按语境判定，判不出时应标「待定」而非判错 |
| **缺字** | 原文此处无字（语料以 `⿰` 标记）。它占一个字符位置，但**不参与判定**——既不合、也不出律、也不待定 |

### 校验结果的三态语义

单字位的判定结果只有三种，**不允许出现第四种**：

| 态 | 含义 | 呈现约束 |
| :--- | :--- | :--- |
| **合** | 实际平仄与词格要求相符 | 中性呈现 |
| **出律** | 实际平仄与词格要求冲突，且该字的读音是确定的 | 必须与「待定」在视觉上可区分 |
| **待定** | 该字为多音字且当前无法确定语境读音，故无法判定 | 提示用户自行确认，**不得呈现为出律** |

「待定」不是失败，是诚实降级。把多音字一律判为出律会让产品不可用——全宋词语料中多音字占 8.8%。

## 数据流

### 构建期

```
上游原始数据  →  清洗（乱码、缺字、异体字）  →  归一化（词牌名、繁简）
            →  紧凑编码（降低前端解析成本）  →  自检（护栏）
            →  静态产物（语料、词谱、韵书、字体子集）
```

管道设计、清洗规则与体积预算见 `docs/design/20-corpus-pipeline.md`。

### 运行期

| 场景 | 载荷 | 行为 |
| :--- | :--- | :--- |
| 打开校验页 | 词谱 | 引擎就绪，逐字实时校验 |
| 阅读某首词 | 零额外载荷 | 构建期已预渲染 |
| 进入搜索页 | 语料全量（一次性，浏览器缓存） | 运行时建索引，之后检索零延迟 |
| 浏览词谱 / 词人 | 按需 | 预渲染页面 |

## 决策索引

以下是已定案的设计决策。改动任一条前须先评估其下游影响。

| # | 决策项 | 结论 |
| :--- | :--- | :--- |
| 1 | 项目名 / 许可 | 一阕 / AGPL-3.0 |
| 2 | 运行形态 | 公开社区平台，以工具站形态起步 |
| 3 | 引擎部署 | 纯前端纯函数，逐字实时校验 |
| 4 | 技术栈 | TypeScript + Next.js(App Router) + antd v6 + Tailwind |
| 5 | 词谱谱系 | 只做《钦定词谱》，817 调 / 2294 体 |
| 6 | 功能边界 | 校验 + 词谱查询 + 词库浏览检索 |
| 7 | 检索 | 纯客户端，运行时建二元索引 |
| 8 | 引擎能力 | L1 + L2 + L3 + L4，L5 后置 |
| 9 | 文本基线 | 修订版全宋词文本 + 自建清洗 |
| 10 | 韵书 | 词林正韵 + 中华新韵，双轨 |
| 11 | URL 结构 | 拼音 slug（词牌/词人）+ 数字 id（词作） |
| 12 | 部署 | 静态托管 + 构建期跑数据管道，开 Brotli |
| 13 | 响应式 | 移动端优先，断点单一来源 |
| 14 | 字体 | 系统宋体栈 + 扩展区 fallback 子集 |
| 15 | 版本记录 | Keep a Changelog + SemVer，tag 驱动 Release |
| 16 | 领域数据形态 | 两层：存储形态（紧凑编码）+ 领域形态（解码对象）。解码在加载时一次性完成 |
| 17 | 词作正文表示 | 原样字符串，保留标点与排版换行。**片/句边界不入存储**，按需从词格推导 |
| 18 | 词格 id | `{词牌 slug}-{字位数}-{同字数内序号}`。正体为**独立字段**，不由 id 或自述推断 |
| 19 | 引擎输入粒度 | 接受「词牌」或「词格」两种粒度；给词牌时返回**候选列表**并自动选中最佳 |
| 20 | 字音条目 | 独立实体，韵书为容器（`韵书 → 字 → 字音[]`）。读法标签可选，由韵书自定 |
| 21 | 缺字表示 | 「字位内容」维度的第三个值（未填 / 缺字 / 已填）。**不产出判定态** |
| 22 | 词作题名 | 可选字段。**语料词作恒为空**（上游数据没有题名），用户作品由用户填写 |
| 23 | 判定与输入状态正交 | 字位层面与整篇层面均严格区分。判定态恒为三值，整体结论恒为三值 |
| 24 | 词格去重 | 字位序列完全重复者去重（产物实测 0 处，护栏常驻），**须在编号前完成** |

各决策的量化依据（体积、覆盖率、性能实测）集中在 `docs/research/competitive-analysis.md`。
