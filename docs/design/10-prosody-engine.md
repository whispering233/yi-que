# 格律引擎设计

格律引擎是本项目的技术核心。它是一个**纯函数层**：输入词牌或词格与词作文本，输出逐字判定结果，全同步、无网络、无框架依赖。

本文描述引擎的**行为**（能力分层、消歧手段、判定语义、质量保障）。数据的**形状**（实体、字段、结果结构）见 `40-data-model.md`。

## 设计原则

1. **数据驱动**：引擎不硬编码任何词牌。全部行为由词谱数据与韵书数据决定。
2. **零框架依赖**：不得引用 React、DOM、Next.js、Node API。否则无法在浏览器直接运行，也无法被未来的服务端复用。
3. **纯函数**：同样的输入必得同样的输出，无副作用、无隐藏状态，可直接单测。
4. **诚实降级**：判不出时标「待定」，不猜测、不误判为出律。

## 领域模型

引擎消费的输入是**词格**：一个有序的字位序列。每个字位含三项要求。

| 字位字段 | 取值 | 含义 |
| :--- | :--- | :--- |
| 平仄要求 | 平 / 仄 / 中 | 中表示平仄皆可，不做判定 |
| 句读标记 | 句 / 读 / 韵 / 叶 / 叠 / 换 / 和声 | 决定断句位置与韵脚位置 |
| 换片标记 | 有 / 无 | 标在该片的最后一个字位 |

**片**（上下阕）由换片标记切分。字数、句数、韵数必须是可校验的结构属性——词谱的自述（如「双调九十五字，前段九句四平韵，后段十句四平韵」）提供了独立的校验基准，详见 `20-corpus-pipeline.md` 的护栏自检。

### 字的两类属性

判定一个字位的合规性，需要知道该字在当前语境下的两个属性：

| 属性 | 来源 | 是否依赖韵书 |
| :--- | :--- | :--- |
| **读音**（取哪个音） | 多音字消歧 | 否 |
| **平仄 / 韵部** | 由读音查韵书得到 | 是 |

这个切分很重要：**消歧逻辑与韵书无关**，换韵书只需换「读音 → 平仄/韵部」的映射表，消歧逻辑不变。因此加一本韵书是加数据，不是改引擎。

## 能力分层

| 层 | 能力 | 状态 |
| :--- | :--- | :--- |
| **L1** | 逐字对谱（平 / 仄 / 中） + 韵脚同韵部判定 + 句读分段 | 交付 |
| **L2** | 多音字语境消歧；判不出时降级为「待定」 | 交付 |
| **L3** | 变格支持：换韵、通叶、错叶、叠韵、拗句标注 | 交付 |
| **L4** | 不给词牌名时自动辨谱（遍历全部词格匹配） | 交付 |
| **L5** | 出律改字建议、笺注、典故分析 | 后置 |

### L1：基础对谱

逐字位比对：字位要求为「中」则跳过；否则比较实际平仄与要求。韵脚位须额外检查是否与该片已出现的韵脚属同一韵部。

韵脚位的判定有一个天然优势：**词的韵脚必然同属一部**，所以一旦某个韵脚字的读音确定，它同时约束了其余韵脚字的候选读音集合。这是消歧时最可靠的信号，应优先使用。

### L2：多音字（已按「存在合律读法即合」定案）

多音字占语料用字的 8.8%，是产品可用性的成败所在。

**定案规则：只要该字存在一个满足要求的读音，就判「合」。** 这不是猜，是「该字存在合律读法」这个**确定的事实**——作者完全可以选那个读音。词学上多音字只要一读合律就算合。

「出律」只在**所有**读音都不满足时才给，因此**不会任取一个读音后判为出律**。

不用「猜读音」的方式消歧（词组表、默认读音）——那就是在猜，且猜错会制造错误的出律。

#### 韵脚约束仍有作用：确定韵部

一片内的所有韵脚**必然同属一个韵部**——这是词体本身的硬约束。多音字在韵脚位有多个候选韵部，靠其余韵脚约束到唯一的一个，界面才能回答「我这一片押对了吗」。

求不出唯一交集就不动，绝不任取一个。

#### 实测

| 口径 | 值 |
| :--- | :--- |
| 词谱自己的例词（772 个词牌 / 24401 字位） | 零出律 743 个（96.2%） |
| 出律 | 34 字位（0.14%） |
| **待定** | **264 字位（1.08%）** |

（改为「存在合律读法即合」之前，待定率是 8.3%。）

剩余的待定字全是在韵书里**查不到**的字（閒 纥 諠 佾 砧 裛 濩…），多为异体字与生僻字。异体字归一化可再降一部分，已记入 `backlog.md`。

### L3：变格

词谱的句读标记已携带变格信息（换韵、通叶、错叶、叠韵），引擎消费标记即可，无需额外规则表：

| 标记 | 引擎行为 |
| :--- | :--- |
| 韵 | 该片内所有韵脚须同韵部 |
| 换 | 此处开启新的韵部约束，前后韵部不同 |
| 叶 | 通叶，允许与相邻韵部通押 |
| 叠 | 该字位须与前一字位相同（叠字/叠韵） |

拗句在词谱中体现为句读与平仄的特定组合，引擎只需按字位要求逐位比对，**不为拗句写特例**——特例会让引擎无法响应词谱数据的变化。

### L4：自动辨谱

不给词牌名时，用词作文本（字数 + 句读模式）先筛出候选词格，再逐一做 L1 校验，返回匹配度最高者。

计算量很小：全部词格合计不足二十万字位，纯字符串比较在浏览器内是毫秒级。**这是 L1 的副产品，不是独立工程。**

匹配到多个词格时，须向用户展示候选列表而非静默取第一个——同一词作出现在多个词牌下是宋词中的常见现象。

### L5 后置的理由

改字建议需要语料统计或模型能力，笺注典故需要知识图谱，两者都是独立的重大工程。**且加上它们不改变引擎架构**——L5 是消费引擎输出与语料统计的新增层，L1–L4 的接口无需变动。

## 引擎接口

引擎接受**两种粒度**的输入：

| 输入 | 行为 |
| :--- | :--- |
| **词格** | 直接校验该词格 |
| **词牌** | 遍历该词牌全部词格，按匹配度排序，返回候选列表并自动选中最佳 |

**为何要两种粒度**：44.7% 的词牌存在「同字数多词格」，用户通常只输入词牌名、**不会知道自己是第几体**。引擎必须能自动选，否则 UI 只能强迫用户在不懂的情况下做选择。

**为何不是两次调用**：匹配就是「逐位判定的副产品」（出律字数最少者胜），不需要单独一次计算。把「匹配」与「校验」拆成两次调用是**把同一次计算拆成两次**。

**L4 复用同一份代码**：L4 自动辨谱是「不给词牌」时遍历全部词格；给词牌时遍历该词牌的几体。**只是输入范围不同，算法完全相同**。

匹配度相同时的决胜规则、字数不足时的退化、以及结果结构的完整字段定义，见 `40-data-model.md`。

## 质量保障

### 回归测试集

全宋词语料是引擎的**金标准测试集**：近两万首真实词作，覆盖 818 个词牌。

测试方式不是要求「全部合规」——宋词实际创作中出律是常态。而是**按词牌统计异常**：

- 某词牌下的词作若大面积无法匹配任何词格，说明**引擎或该词牌的词格数据有 bug**，而不是古人集体出律
- 修复引擎或词谱数据后，该词牌的匹配率须回到正常区间

这组测试同时是词谱数据质量的护栏，引擎与数据互为验证。

### 词牌名归一化是前提

上游语料的词牌名与词谱的词牌名并非一一对应：组合写法（别名・正名）、别名、繁简与异体字差异。归一化映射表是引擎能接手真实语料的前提，其设计见 `20-corpus-pipeline.md`。

### 待测边界

- 多音字在韵脚位、非韵脚位、单字成句三种情形下的判定
- 换韵、通叶、错叶、叠韵词牌的正确分片与韵部约束
- 变体词格（同一词牌下多个格式）的候选筛选与决胜规则的确定性
- **缺字位（`⿰`）所在字位的处理——不得计入出律，也不得落进「待定」**
- **填到一半的输入**（字数少于词格）：已填位正常判定，未填位不产出判定态
- 语料覆盖之外的长尾词牌：引擎须优雅报告「无匹配词格」而非抛错
