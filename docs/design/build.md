# 运行、构建与部署

## 开发环境

| 项 | 要求 |
| :--- | :--- |
| Node.js | 22 LTS 或更高 |
| 包管理器 | pnpm |
| 数据库 | **不需要**。工具站阶段无服务端、无数据库 |
| 容器 | **不需要**。容器仅在社区阶段本地跑 PostgreSQL 时才需要 |

数据管道在开发环境的首次运行会拉取上游数据源，需要网络。

## 构建流程

构建分两个阶段，**顺序不可颠倒**。

```
① 数据管道（构建期）
   拉取/读取上游数据源
     → 清洗 → 归一化 → 紧凑编码
     → 生成字体子集
     → 护栏自检（不通过即失败）
     → 写出静态产物

② 应用构建
   静态产物 + 应用代码
     → Next.js 静态导出
     → Brotli 预压缩
     → 部署产物
```

### 关键性质

- **管道失败必须让构建失败**。护栏自检的任何一项不通过都不得降级为警告——上游错误进入产品后，用户看到的是错字和错误的校验结果
- **上游数据不入版本控制**，静态产物也不入版本控制。只有管道代码入版本控制，构建可复现
- **产物是可丢弃的**。任何时候删除产物重新构建，结果应当一致

### 构建产物体积预算

| 产物 | Brotli 上限 |
| :--- | :--- |
| 词谱（首屏必需） | 400KB |
| 词库语料 | 2.2MB |
| 扩展区 fallback 字体 | 50KB |
| 韵书 | 80KB |

超出预算说明引入了冗余，须在合并前查明原因。

## 部署

工具站阶段为**纯静态站点**，可部署到任何静态托管平台，无需服务端。

### 当前托管：GitHub Pages

工作流：`.github/workflows/deploy.yml`（push 到 main 触发）。产物路径 `out/`（Next.js 静态导出）。

**三处必须知道的限制：**

#### 一、路径前缀会改变 URL

GitHub Pages 的项目页形式是 `https://<user>.github.io/<repo>/`，**有路径前缀**。因此构建时须设 `NEXT_PUBLIC_BASE_PATH=/<repo>`，由构建配置消费。

换用自定义域名后站点在根路径，该前缀须**置空**——届时 URL 会整体变化。

> **对 URL 契约的影响**：`30-web-app.md` 冻结的是**路径结构**（`/tune/{slug}`、`/ci/{id}`），不是站点根前缀。根前缀属部署配置，迁移时整体变化，不破坏站内结构。但**外部链接会失效**——这在前缀期间是有代价的，所以尽早接自定义域名。

#### 二、Brotli 不确定，载荷须按 gzip 计

GitHub Pages **不支持自定义响应头**，无法自己控制压缩算法。是否提供 Brotli 须**实测**（部署后 `curl -H 'Accept-Encoding: br' -I <url>` 看响应头）。

若只有 gzip，载荷预算须按 gzip 重算：

| 产物 | Brotli（理想） | gzip（GitHub Pages 下限） | 差距 |
| :--- | :--- | :--- | :--- |
| 词谱（首屏） | 386KB | 581KB | +51% |
| 语料（搜索页） | 2.08MB | 2.77MB | +33% |

**这不改变架构**（仍是纯静态、客户端检索），只影响加载时长。若实测只有 gzip 且移动端体验不可接受，再评估换托管。

#### 三、中国大陆访问不稳定

`github.io` 在中国大陆访问不稳定。对中文产品而言这是**实质性限制**。

当前选它是因为**零成本、无需备案、与仓库集成**，适合拿到真实反馈。待有明确流量数据后再评估备案迁回国内。

### 部署要求

| 项 | 要求 | 理由 |
| :--- | :--- | :--- |
| 自动 HTTPS | 必须 | — |
| 自定义域名 | 支持 | 便于后续迁移与备案；也能去掉路径前缀 |
| 长缓存 | 静态产物可长缓存 | 产物名带内容指纹，改内容即改文件名 |
| `.nojekyll` | 必须 | Jekyll 会跳过下划线开头的目录，Next.js 的 `_next/` 在其中 |

### 托管迁移

因为是无状态静态站点，**迁移只需改 DNS 与一处路径前缀配置**。但须保证：

- URL **路径结构**不变（见 `30-web-app.md` 的路由契约）
- 若迁移至中国大陆托管，需先完成域名备案

### 中国大陆访问

工具站阶段优先选择无需备案即可发布的托管方式，以获得真实用户反馈；待有明确流量数据后再评估是否备案迁回。

## 发布流程

版本记录遵循 **Keep a Changelog** 与**语义化版本**。

### 发布步骤

1. 在 `CHANGELOG.md` 中把 `[Unreleased]` 段的条目归入新的版本段，版本头形如 `## [vX.Y.Z] - YYYY-MM-DD — <主题>`
2. 提交并推送
3. 打 tag 并推送：`git tag vX.Y.Z && git push origin vX.Y.Z`
4. GitHub Actions 自动从 `CHANGELOG.md` 摘取匹配该 tag 的版本段，创建 GitHub Release

### CHANGELOG 写作规范

- **版本头**可带一行主题后缀，主题可标注性质（如「文档收敛（无功能变更）」）
- **正文只写条目**，标准节：`Added` / `Changed` / `Fixed` / `Removed` / `Docs` / `Security`
- **说明节**用于需要单独提醒的内容：`Note` / `Breaking` / `过渡注意`
- **不写引用块摘要段**——它只会重述条目，并夹带回归证据（测试计数、取证过程）这类不属于本文件的内容
- **不混入任务卡语义**（「卡N」「批次N」等）——任务卡是临时工作方式，其他开发者无法识别
- 升级提醒、迁移注意事项要写进条目或说明节，**不能只出现在别处**——因为 CHANGELOG 是 Release 正文的唯一来源

### 版本号含义

| 变更 | 版本位 |
| :--- | :--- |
| 破坏性变更（URL 契约、数据格式、引擎判定语义） | 主版本 |
| 新增功能、新增词牌/韵书数据 | 次版本 |
| 修复、文档、样式调整 | 修订号 |

**URL 契约变更视为破坏性变更**——已收录页面失效是实质影响。

- 页脚的源码入口链接存在且可达（AGPL-3.0 义务）
- 第三方数据来源与许可标注完整
