# 数据结构 Schema

## 当前状态：无数据持久化

工具站阶段是**纯静态应用**：无服务端、无数据库、无用户数据。全部内容（词库、词谱、韵书）在构建期由数据管道产出为静态产物，用户的操作（校验、检索、浏览）全部在浏览器内完成。

静态产物的结构设计见 `../design/20-corpus-pipeline.md`，不在本文重复。

## 现在已确定的持久化约束

以下约束在社区阶段实现时**必须遵守**，因为它们已经外显为用户可见的契约：

| 约束 | 理由 |
| :--- | :--- |
| 词作使用**稳定数字 id** | 词作详情页的 URL 使用 id。上游语料持续校勘，若 id 不稳定则 URL 失效、已收录页面丢失 |
| 词牌、词人使用**稳定 slug** | 同上。slug 与数字 id 均不得因内容修订而变化 |
| 词作正文须能追溯**数据版本** | 上游文本会修订。用户引用或分享的内容若在校勘后变化，需能判断差异来源 |
| 用户作品与词库语料**分表** | 语料是只读的构建产物，用户作品是可写数据。两者混放会导致同步、备份、许可边界全部混乱 |

## 社区阶段的 Schema

社区阶段的数据模型取决于该阶段的功能设计（账号体系、作品发布、评论互动、审核机制），**这些功能尚未设计**。

**现在不预先规定表结构**——为一个尚未设计的功能定义字段，产出的是猜测而非设计，且会成为后续讨论的锚点偏差。

进入社区阶段时的设计顺序：

1. 先确定社区功能范围与用户流程
2. 再确定数据模型，写入本文
3. 再确定 API 契约，写入 `../api/`

### 设计时的硬约束

- 用户作品与词库语料必须隔离
- 用户作品的删除语义须明确（软删除 vs 物理删除），且不可逆操作要有确认
- 涉及用户生成内容，须在设计期一并考虑举报与审核的数据承载
